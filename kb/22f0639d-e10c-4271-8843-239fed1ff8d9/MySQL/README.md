# MySQL

## 1. 事务 ACID 特性
- **原子性**：事务是最小的执行单元，要么全部成功，要么全部失败回滚（通过undo log实现）。
- **一致性**：事务执行前后，数据库从一个一致性状态转换到另一个一致性状态（这是最终目的）。
- **隔离性**：并发事务之间互不干扰（通过锁和MVCC实现）。
- **持久性**：事务提交后，数据修改永久保存（通过redo log实现）。

## 2. 索引原理与设计
- **数据结构**：B+树（多路平衡查找树），叶子节点形成有序链表，适合范围查询。
- **聚簇索引 vs 非聚簇索引**：聚簇索引（主键索引）叶子节点存整行数据；非聚簇索引（二级索引）叶子节点存主键值，查询可能需要回表。
- **覆盖索引**：查询所需的所有列都包含在索引中，无需回表，极大提升性能。
- **最左前缀原则**：联合索引（a,b,c）可支持 `a`、`a,b`、`a,b,c` 的查询，但无法跳过中间列使用。
- **索引失效场景**：对索引列进行函数或运算、使用 `LIKE` 左模糊、使用 `OR` 且条件未都走索引、类型隐式转换等。

## 3. 锁机制与事务隔离
- **锁类型**：表锁、行锁（记录锁、间隙锁、临键锁）、意向锁。
- **行锁实现**：基于索引，无索引时退化为表锁。
- **死锁**：两个或多个事务互相持有对方所需的锁。处理：等待超时、死锁检测（`innodb_deadlock_detect`）。
- **四种隔离级别**：
    - 读未提交：可能脏读、不可重复读、幻读。
    - 读已提交：解决脏读（MVCC每次读生成新快照）。
    - 可重复读：解决脏读、不可重复读（MVCC事务开始时生成快照）。
    - 可串行化：完全串行执行，解决所有问题但性能最差。

## 4. MVCC (多版本并发控制)
- **核心机制**：通过数据行的隐藏字段（`trx_id`, `roll_pointer`）和 `undo log` 版本链，实现非锁定读。
- **Read View**：事务进行快照读时生成，包含当前活跃事务列表，用于判断哪个版本的数据对当前事务可见。
- **与隔离级别关系**：RC（每次SELECT生成新Read View） vs RR（事务内首次SELECT生成，后续复用）。

## 5. SQL 优化与查询分析
- **EXPLAIN 详解**：重点看 `type`（访问类型，`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`）、`key`（实际使用索引）、`rows`（预估扫描行数）、`Extra`（`Using index`覆盖索引、`Using filesort`、`Using temporary`）。
- **优化要点**：
    - 避免 `SELECT *`，只查需要的列。
    - 确保 `WHERE`、`ORDER BY`、`JOIN ON` 字段有索引。
    - 小表驱动大表。
    - 优化 `LIMIT` 分页（使用基于游标的分页）。
- **慢查询日志**：`slow_query_log` 开启，分析 `long_query_time` 之后的查询。

## 6. MySQL 架构与执行流程
- **逻辑架构**：
    1. **连接层**：管理连接，验证权限。
    2. **服务层**：解析、优化、缓存（8.0后移除查询缓存）、执行器。
    3. **引擎层**：存储和提取数据。
- **一条SQL的执行流程**：连接器 -> 查询缓存(8.0前) -> 解析器 -> 优化器 -> 执行器 -> 存储引擎。

## 7. InnoDB 存储引擎核心特性
- **事务支持**：支持ACID，通过redo/undo log保证。
- **行级锁**：实现高并发，提高性能。
- **MVCC**：实现非锁定读。
- **崩溃恢复**：redo log保证持久性，undo log保证原子性。
- **表空间**：数据和索引存储在表空间文件（`.ibd`）中。
- **与MyISAM对比**：MyISAM不支持事务、行锁、外键，崩溃恢复差，但读性能好。

## 8. 主从复制原理与优化
- **复制过程**：`Master`写`binlog` -> `Slave`的`IO线程`拉取`binlog`写入`relay log` -> `SQL线程`重放`relay log`。
- **复制类型**：
    - **异步复制**（默认）：Master不等Slave确认，有延迟风险。
    - **半同步复制**：至少一个Slave确认收到`binlog`后Master才返回。
- **主从延迟**：可通过并行复制（`slave_parallel_workers`）、优化网络和单线程重放瓶颈解决。

## 9. 分库分表与读写分离
- **垂直拆分**：按业务拆库/表，减少单库/表压力。
- **水平拆分**：按数据键（如`user_id`）将同一表数据拆到多个库/表，解决数据量问题。
- **读写分离**：主库写，从库读，通过中间件（如MyCat、ShardingSphere）实现。
- **分布式ID**：常用雪花算法、UUID、数据库序列等生成全局唯一ID。

## 10. 慢查询分析与优化实战
- **分析工具**：`EXPLAIN`、`SHOW PROFILE`、`performance_schema`、慢查询日志。
- **优化步骤**：
    1. 检查是否缺少合适索引。
    2. 分析执行计划，查看是否有多余的排序、临时表。
    3. 优化SQL写法，避免复杂子查询，考虑JOIN重写。
    4. 考虑是否为热点数据，考虑缓存方案。
- **常见陷阱**：索引失效、大数据量分页、`COUNT(*)`性能、`NOT IN`和`!=`可能无法利用索引。

## 11. 事务锁冲突与死锁排查
- **查看当前锁**：`SHOW ENGINE INNODB STATUS`、`performance_schema.data_locks`。
- **死锁排查**：
    1. 查看 `performance_schema.data_lock_waits`。
    2. 分析 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 部分。
- **预防死锁**：
    - 按固定顺序访问表和行。
    - 事务尽量短小。
    - 使用合理的索引，减少锁范围。
    - 适当降低隔离级别（如RC）。

## 12. 数据一致性（主从延迟与选主）
- **主从延迟问题**：从库读到旧数据。解决：关键读走主库、使用半同步复制、设置延迟容忍、检查并优化从库重放性能。
- **高可用选主**：`MHA`、`Orchestrator`、`ZooKeeper`、`Raft`等实现自动故障转移和主从切换。
- **数据一致性终极方案**：`Paxos`/`Raft`协议（如MySQL Group Replication、InnoDB Cluster）。
