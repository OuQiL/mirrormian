# Redis

## 1. 核心数据结构与底层实现
- **五大基础类型**：String, List, Hash, Set, Sorted Set。理解每种类型的典型使用场景（如 Sorted Set 用于排行榜）。
- **扩展类型**：Bitmap, HyperLogLog, Geospatial, Streams。了解其独特用途（如 Bitmap 统计用户活跃天数）。
- **底层数据结构**：简单动态字符串、链表、字典（哈希表）、跳跃表、整数集合、压缩列表等。理解其对性能和内存的影响。
- **面试考点**：特定场景下如何选择数据类型；Redis 如何通过底层结构优化性能和内存。

## 2. 高性能线程模型
- **单线程与多路复用**：核心命令处理线程是单线程的，通过 I/O 多路复用技术（如 epoll）处理并发连接，避免上下文切换和锁开销。
- **6.0 以后的多线程**：网络 I/O（读/写）阶段引入多线程，但命令执行仍是单线程，旨在利用多核 CPU 提升网络吞吐。
- **面试考点**：为什么单线程还能这么快？多线程后是否线程安全？

## 3. 持久化机制（RDB 与 AOF）
- **RDB（快照）**：在某个时间点将内存数据生成二进制快照并持久化到磁盘。优缺点：恢复快，但可能丢失最后一次快照后的数据。
- **AOF（追加日志）**：记录每个写命令。三种同步策略：always, everysec, no。优缺点：数据更安全，但文件大、恢复慢。
- **混合持久化**：4.0+ 支持，AOF 重写时使用 RDB 格式作为开头，后续追加 AOF 日志，结合两者优点。
- **面试考点**：如何选择持久化策略？生产环境如何配置？数据丢失场景分析。

## 4. 内存管理与淘汰策略
- **内存分配**：使用 jemalloc 等内存分配器，减少内存碎片。
- **内存淘汰策略**：8 种策略，重点掌握 `volatile-lru`, `allkeys-lru`, `volatile-lfu`, `allkeys-lfu`, `no-eviction` 等。理解“近似 LRU/LFU”算法原理。
- **大 Key 问题**：什么是大 Key？如何发现（`redis-cli --bigkeys`）？如何避免和删除（异步删除 `UNLINK`）？
- **面试考点**：生产环境如何设置最大内存？如何分析和解决内存占用过高问题？

## 5. 高可用架构：主从复制
- **原理**：全量同步（RDB）与增量同步（基于偏移量的 repl_backlog）。
- **作用**：数据备份、读写分离（从节点分担读流量）、故障快速恢复。
- **面试考点**：主从复制过程中如果发生故障，数据会丢失吗？增量同步在什么条件下会失效？

## 6. 高可用架构：哨兵（Sentinel）
- **核心功能**：监控（master/slave 是否正常工作）、通知（故障时发送通知）、自动故障转移（选举新 master 并通知客户端）。
- **选举算法**：Raft 算法的简化版，用于选举 leader 哨兵执行故障转移。
- **面试考点**：哨兵如何判断主节点客观下线？故障转移期间如何保证服务可用性？

## 7. 分布式架构：Redis Cluster
- **数据分片**：16384 个哈希槽（Hash Slot），通过 `CRC16(key) % 16384` 映射到不同节点。
- **节点通信**：Gossip 协议，用于节点间交换状态信息。
- **故障转移**：与哨兵类似，在集群内部完成 master 和 slave 的故障转移。
- **面试考点**：集群如何扩容和缩容（在线迁移 slot）？客户端如何定位数据（MOVED/ASK 重定向）？

## 8. 事务与 Lua 脚本
- **事务**：通过 `MULTI/EXEC/DISCARD/WATCH` 实现，保证命令序列的原子性执行（但非严格意义上的 ACID）。
- **Lua 脚本**：`EVAL` 命令在服务器端原子性执行。功能更强大，可实现复杂原子操作（如 CAS）。
- **面试考点**：Redis 事务与数据库事务的区别？WATCH 命令的乐观锁机制如何使用？

## 9. 发布订阅与 Stream
- **Pub/Sub**：轻量级的发布订阅模型，但消息不持久化，不支持消费者组，可能丢失消息。
- **Stream（5.0+）**：持久化的、支持消费者组的消息队列，提供了消息 ID、ACK 机制，功能更完善，可替代部分 MQ 场景。
- **面试考点**：如何选择 Pub/Sub 和 Stream？如何使用 Stream 实现可靠的消费？

## 10. 性能分析与优化
- **慢查询日志**：记录执行时间超过阈值的命令，用于定位性能瓶颈。
- **基准测试工具**：`redis-benchmark`。
- **客户端优化**：Pipeline（批量命令减少 RTT）、连接池。
- **服务器优化**：避免复杂 O(N) 命令、使用小 Key、合理设置过期时间。
- **面试考点**：如何排查线上 Redis 变慢的问题？Pipeline 的原理和注意事项。

## 11. 常见陷阱与最佳实践
- **缓存三大问题**：穿透（布隆过滤器）、击穿（互斥锁）、雪崩（随机过期、熔断降级）。
- **Key 设计**：使用 `业务前缀:ID` 格式，避免使用过长、过大的 Key。
- **热 Key 问题**：识别与解决（本地缓存、读写分离、Key 分散）。
- **删除安全**：使用 `DEL` 可能阻塞，对大 Key 改用 `UNLINK` 进行异步删除。
- **序列化**：选择高效的序列化方式（如 Protobuf、Kryo）而非原生的 Java 序列化。
- **安全**：设置 `requirepass`，禁用危险命令（`rename-command`）。

## 12. 监控与运维
- **关键指标**：`INFO` 命令查看（内存、QPS、连接数、命中率等）。
- **持久化监控**：检查 `last_save_time` 和 `rdb_last_bgsave_status`。
- **日志分析**：监控慢查询日志和运行日志。
- **备份策略**：结合 RDB 和 AOF，并定期将备份文件异地存储。
